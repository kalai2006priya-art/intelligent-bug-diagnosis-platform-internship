# M1.4 - Historical Defect Dataset Analysis

## 1. Objective

The objective of this analysis is to inspect and understand historical software defect datasets that will be used to build the Historical Defect Knowledge Base for the Intelligent Bug Diagnosis Platform.

The datasets are analyzed to identify their structure, important fields, missing values, and useful attributes for later cleaning, chunking, embedding generation, and semantic retrieval.

---

## 2. Datasets

The project uses historical software defect data from the following sources:

- Eclipse
- Apache
- Mozilla

The datasets are stored under the project's `data` directory.

---

## 3. Eclipse Dataset

### File

`data/eclipse/eclipse_bug_report_data.csv`

### File Size

Approximately 10.32 MB.

### Number of Columns

19 columns.

### Important Fields

- `bug_id`
- `creation_date`
- `component_name`
- `product_name`
- `short_description`
- `long_description`
- `resolution_category`
- `resolution_code`
- `status_category`
- `status_code`
- `resolution_date`
- `bug_fix_time`
- `severity_category`
- `severity_code`

### Sample Analysis

The dataset was inspected using a sample of 5,000 rows.

Missing values were observed in the `long_description` field.

The `severity_category` field contains categories such as:

- normal
- major
- minor
- critical
- blocker
- trivial

The `component_name` field contains different software components such as UI, Core, SWT, TPTP, Releng, and others.

### RAG Relevance

The following fields are particularly useful for the RAG knowledge base:

- `short_description`
- `long_description`
- `component_name`
- `product_name`
- `resolution_category`
- `severity_category`

These fields can provide information about the problem, affected component, severity, and historical resolution.

## 6. Mozilla Dataset

The project includes a Mozilla historical bug dataset as part of the planned knowledge base.

The Mozilla dataset path and file availability are being verified before processing.

---

## 7. Initial Observations

The analysis shows that different datasets use different field names and structures.

For example:

Eclipse uses:

`short_description`

Apache uses:

`summary`

Therefore, a common standardized schema is required before creating the RAG knowledge base.

The datasets also contain missing values, especially in optional fields such as descriptions, resolutions, assignees, and priorities.

---

## 8. Proposed Standard Schema

The historical defect datasets will be standardized into the following common fields:

| Standard Field | Purpose                   |
| -------------- | ------------------------- |
| bug_id         | Unique identifier         |
| source         | Dataset source            |
| project        | Project or product        |
| component      | Affected component        |
| title          | Short bug description     |
| description    | Detailed bug description  |
| comments       | Historical discussion     |
| severity       | Bug severity              |
| priority       | Bug priority              |
| status         | Current/historical status |
| resolution     | Historical resolution     |
| created_at     | Bug creation date         |
| resolved_at    | Resolution date           |
