# Milestone 1.1 – Research & Technical Understanding

## 1. Defect Analysis Workflow

Software defect analysis is the process of identifying, analyzing,
diagnosing, and resolving software defects.

### Typical Defect Analysis Workflow

1. Bug Report Submission
2. Bug Triage
3. Log and Stack Trace Analysis
4. Problem Reproduction
5. Root Cause Analysis
6. Duplicate / Similar Bug Detection
7. Fix Recommendation
8. Fix Verification
9. Defect Resolution

### Mapping to the Proposed AI Platform

| Defect Analysis Activity | Proposed System Component |
|---|---|
| Bug Report Submission | Bug Submission Module |
| Bug Triage | Triage Agent |
| Log Analysis | Log Analysis Agent |
| Root Cause Analysis | Root Cause Agent |
| Duplicate Detection | Duplicate Detection Agent |
| Fix Recommendation | Remediation Agent |
| Historical Defect Search | RAG + Vector Search |

## 2. Retrieval-Augmented Generation (RAG)

Retrieval-Augmented Generation (RAG) is an approach that combines information retrieval with a Large Language Model (LLM).

Instead of relying only on the knowledge stored within the language model, RAG retrieves relevant information from an external knowledge base and provides it as context to the LLM.

### RAG Workflow in the Proposed Platform

1. Receive the current bug report, stack trace, or error log.
2. Process and normalize the submitted information.
3. Convert the processed bug information into an embedding.
4. Search the historical defect vector database using semantic similarity.
5. Retrieve the most relevant historical defect records.
6. Provide the retrieved information as context to the LLM.
7. Generate diagnosis and fix recommendation using the retrieved context.

### Proposed RAG Flow

Current Bug
→ Embedding Generation
→ Vector Search
→ Similar Historical Defects
→ Retrieved Context
→ LLM
→ Diagnosis and Fix Recommendation

### Benefits of RAG for Bug Diagnosis

- Uses historical software defect knowledge.
- Helps retrieve similar previously reported bugs.
- Provides relevant context to the language model.
- Can reduce dependence on the LLM's general knowledge.
- Supports evidence-based bug diagnosis and fix recommendations.

- ## 3. Semantic Similarity

Semantic similarity is the process of measuring how similar two pieces of text are in terms of their meaning.

In the proposed bug diagnosis platform, semantic similarity is used to compare a newly submitted bug with historical bug reports.

### Example

Current Bug:
"Application crashes when the user clicks the login button."

Historical Bug:
"System terminates unexpectedly during user authentication."

Although the exact words are different, both reports describe a similar problem. Therefore, they can have a high semantic similarity score.

### Semantic Similarity Workflow

1. Receive the current bug report.
2. Convert the bug report into an embedding.
3. Compare the embedding with historical defect embeddings.
4. Calculate similarity scores.
5. Rank historical defects based on similarity.
6. Retrieve the most relevant defects.

### Keyword Search vs Semantic Search

| Keyword Search | Semantic Search |
|---|---|
| Searches for matching words | Searches based on meaning |
| May miss similar bugs with different wording | Can identify differently worded but similar bugs |
| Mainly text matching | Uses vector representations |
| Less suitable for complex bug descriptions | Suitable for historical defect retrieval |

### Importance in the Proposed Platform

Semantic similarity helps the system identify previously reported defects that are similar to a new bug, even when the wording is different. This supports duplicate detection, historical defect retrieval, root cause analysis, and fix recommendation.
